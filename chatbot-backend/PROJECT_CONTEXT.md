# Контекст проекта

## Кто я

Fullstack-разработчик: React / React Native / .NET. Перехожу в AI Engineering.
Цель — remote-продуктовые компании. Python осваиваю по ходу; привычки из C#

Работаю в режиме «сначала объясни замысел, потом код». Не пиши реализацию
сразу на ключевых решениях (схема БД, чанкинг, промпты, метрики) — сначала
опиши подход, я решу. На рутине (парсеры, docker, фронтенд) можно сразу код.

## Что строим

RAG-ассистент по документации одной библиотеки. Учебный проект, но должен
выглядеть как продакшен — это портфолио для собеседований.

Ключевая идея: ценность проекта не в работающем демо, а в **измеримой
истории улучшений**. Главный артефакт — таблица в README:
изменение → метрики до → метрики после.

## Стек (решено, не пересматриваем)

- Python 3.12, uv, FastAPI, всё async
- Postgres 17 + pgvector, asyncpg напрямую
- **Без ORM.** Голый SQL, репозитории. Миграции — .sql файлы + свой раннер
  на asyncpg с таблицей schema_migrations
- **Без LangChain** до этапа агентов (этап 4). Провайдеры вызываем напрямую
- Провайдер-агностичный слой: Protocol-интерфейсы LLMProvider /
  EmbeddingProvider, реализации Anthropic + OpenAI, переключение конфигом
- Эмбеддер: text-embedding-3-small, 1536 измерений
- Langfuse (self-hosted в том же compose) — подключён с этапа 1
- Деплой: AWS, ECS/App Runner, RDS. Не Lambda (стриминг + холодные старты)
- React-фронтенд со SSE-стримингом

## Схема БД

documents: id, title, source_uri, version, created_at
chunks: id, doc_id, chunk_index, content, section_title, meta jsonb,
embedding vector(1536), embed_model text,
tsv tsvector GENERATED ALWAYS AS (to_tsvector('russian', content)) STORED

Индексы: GIN по tsv. **HNSW не создавать** — нужен точный перебор как
эталон для замера recall.

## Правила кода

- Retrieval-запросы — сырой SQL, не абстракции
- Никогда SELECT \*
- `embedding` никогда не перечисляется в SELECT и RETURNING — только в
  вычислениях (embedding <=> $1) и в INSERT
- Списки колонок — в константах, чтобы SELECT и RETURNING не расходились
- Промпты — отдельные версионируемые файлы в src/generation/prompts/
- `embed_model` пишется рядом с вектором: смена модели = переиндексация
- register_vector из pgvector.asyncpg — иначе вектор склеивается в строку
- Любое изменение retrieval требует прогона evals до и после

## Этапы

0. **Датасет** (делаю сам, без кода). evals/dataset/golden.jsonl, 60 вопросов
   с эталонными ответами. Пропорции: 40% фактических, 20% многошаговых,
   15% невозможных (ответа в корпусе нет — система должна отказаться),
   15% с фильтрацией, 10% неоднозначных.
   Формат: {id, question, expected_answer, expected_source_ids,
   category, must_include, must_not_include}
1. **Чат.** FastAPI + SSE-стриминг, подсчёт токенов и стоимости, ретраи с
   экспоненциальным бэкоффом, Langfuse. Без retrieval.
2. **Наивный RAG + baseline.** Фиксированный чанкинг 500/50, эмбеддинги,
   ORDER BY embedding <=> $1 LIMIT 5 **без индекса**. Первый прогон evals.
   Цифры будут плохими — это точка отсчёта, так и надо.
3. **Итерации** (ядро проекта). По ОДНОМУ изменению, после каждого прогон
   evals и строка в таблицу README:
   - чанкинг по структуре документа, заголовок секции в каждый чанк
   - гибридный поиск: вектор + GIN, склейка через RRF (CTE + FULL OUTER JOIN)
   - реранкер поверх top-20 → top-5
   - переписывание запроса для многошаговых вопросов
   - обязательное цитирование chunk_id в ответе
   - порог по distance → отказ «в документации этого нет»
   - HNSW-индекс — и сразу замер recall против точного перебора
4. **Агент.** Здесь можно LangGraph. 3-4 инструмента, лимит шагов, детект
   зацикливания, обработка отказов инструментов, тест на prompt injection,
   потолок стоимости сессии.

## Метрики evals

- must_include hit rate (простая проверка подстроки, без LLM-судьи)
- refusal accuracy на category=impossible — самая важная метрика
- context recall: попал ли expected_source_id в выдачу retrieval
- faithfulness (LLM-судья, только для многошаговых)
- p50/p95 латентности, стоимость на запрос
- recall@10 индекса против точного перебора

Результаты в evals/results/{N}-{name}.json, коммитятся в git.
CI гоняет сокращённый датасет (~20 вопросов) на каждый PR, валит сборку
при падении метрик больше 5%.

## README — главный артефакт

Проблема → схема архитектуры → таблица итераций с метриками →
**раздел «где не работает»** (важнее раздела про успехи) →
стоимость и латентность → границы масштабирования → запуск одной командой.

Формулировка про границы (проверенная, использовать её):

> HNSW требует индекс в RAM во всех реализациях. У pgvector средства
> снижения — только сжатие (halfvec, бинарная квантизация); работа с диска
> через pgvectorscale/DiskANN; шардирования векторного индекса нет.
> Потолок — одна машина. При выходе за него: Qdrant (диск и квантизация
> из коробки, фильтр внутри обхода графа) или Milvus (горизонтальное
> масштабирование).

Плюс абстракция VectorStore (Protocol с upsert/search) — чтобы смена
хранилища была локальной.

## Что НЕ делаем

- Не создаём HNSW без явной просьбы
- Не меняем модель эмбеддингов без переиндексации корпуса
- Не хардкодим порог distance — только конфиг
- Не тащим SQLAlchemy: на двух таблицах она даёт больше зависимости,
  чем пользы
- Не оптимизируем выбор эмбеддера и векторной базы: качество RAG определяют
  чанкинг → гибридный поиск → реранкинг, и только потом индекс
- Не файнтюним модели, не пишем свой векторный поиск
